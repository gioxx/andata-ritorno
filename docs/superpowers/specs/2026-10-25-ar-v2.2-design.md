# A/R v2.2 — rotation, categories, platform polish — design

Date: 2026-10-25 · Status: awaiting owner approval · Builds on: `2026-10-23-ar-v2-design.md` (v2.1 is live at ar.gioxx.org)

## Intent

A/R is in daily use on Android with real data. Three things came up from real use and from making the app public: some photos were taken in landscape and need rotating; clothes need a quick way to be filtered by type; and a public app must also work on iPhone, in English, for screen-reader users, and be robust. Everything stays local-first: no server, no account.

## Goals

1. **Rotate a photo** from inside the app.
2. **Categories** (one per item) with **tap-to-filter tags**.
3. **Android system navigation bar** readable in light and dark theme.
4. **iOS compatibility** (Safari + installed PWA on iPhone).
5. **Accessibility** pass.
6. **Languages**: Italian and English.
7. **Hardening**: security headers, robust storage upgrades, large backups, the deferred minors from v2.

## Non-goals

- Family sharing, accounts, sync, payments (projects 2 and 3).
- Per-item movement history.
- More than one category per item, or free tags.
- Languages beyond Italian and English.

## Anti-goals

- Losing or corrupting any existing photo or item when the database schema is upgraded or a photo is rotated (rotation replaces the photo only after "Salva").
- Making the core flow (open → tap items → move) slower or more crowded. Filters must be optional and clear in one tap.

## 1. Rotation (decided with the owner)

- **One** rotate button (rotates 90° clockwise each tap; tap again to keep turning) — lucide `rotate-cw`, label "Ruota" / "Rotate".
- Where: in the **edit dialog** under the photo preview, and in the **full-screen viewer** next to "Modifica".
- Behaviour: the preview shows the rotated result immediately; the change is committed only on **Salva** (edit dialog). In the viewer, "Ruota" opens the same pending-rotation state and shows "Salva" / "Annulla" until confirmed — the original photo is never replaced without an explicit save.
- Viewer state while a rotation is pending (my call): swipe to other items is disabled; closing the viewer (X, Chiudi, Android back, swipe down, Escape) discards the pending rotation; "Salva" commits it as one change. Same rule in the edit dialog: Annulla discards.
- Implementation: pixels are really rotated (canvas, from the decoded original at its own resolution, no downscaling), re-encoded WebP q≈0.92 (JPEG fallback as today), stored as a new photo via the existing replace-photo path (old blob deleted in the same transaction, `updatedAt` bumped, one unsaved change). Backups therefore contain rotated photos. Rotating 4 times then saving is a no-op: if net rotation is 0°, nothing is written. Each saved rotation re-encodes once (small generational loss, accepted); stored photos carry no EXIF orientation (they were produced by canvas), so orientation handling is not needed (my call).

## 2. Categories (decided with the owner)

- **One category per item** (optional; items may have none).
- **Global** across tabs (a pair of trousers is trousers at Nido and Materna).
- **Defaults only on request** (decided by the owner): nothing is created automatically, neither on upgrade nor on new installs. "Gestisci categorie" has a button **"Aggiungi le categorie predefinite"** / "Add the default categories" that adds whichever defaults are missing: Body, Maglie, Pantaloni, Vestiti, Felpe e giacche, Pigiami, Intimo, Calze, Accessori (EN: Bodysuits, Tops, Trousers, Dresses, Sweatshirts & jackets, Pyjamas, Underwear, Socks, Accessories). The button is shown while at least one default is missing (so a deleted default can be brought back on purpose). When no categories exist, the category row in the add/edit dialogs shows a short hint linking to "Gestisci categorie". Default categories show in the current UI language until the user renames them; renamed or user-created ones are shown as typed.
- **Manage** like tabs: add, rename, reorder, delete. Deleting a category with items asks confirmation and leaves those items uncategorised (never deletes items).
- **Assign**: in the add dialog (same dialog as "A scuola / A casa", optional chip row) and in the edit dialog.
- **Filter**: a horizontal row of category tags above the sections, only when at least one item in the current tab has a category. Tap a tag → only items of that category are shown; tap more tags → items of **any** selected category (OR). A "Tutti ✕" / "All ✕" tag clears filters in one tap and is always visible while a filter is active. Section counters show the filtered count; "select all" via the counter selects only visible items. The filter is per session (resets on reload) and per tab switch keeps or clears — **clears** on tab switch (builder may revisit if confusing).
- Default ids are fixed and derived from the key (e.g. `default-body`, `default-socks`), so two devices that both have the defaults merge into one set instead of duplicates (my call). Importing an older backup may bring back a deleted category, exactly like tabs today (accepted, no tombstones in v2).
- Data: new `categories` store `{ id, name, nameKey?, order, createdAt, updatedAt }` (`nameKey` set for untouched defaults, used for translation; cleared on rename). `Item.category` (already in the model, unused) holds the category id. Merge: categories merge by id with their own `updatedAt`, like tabs; item `category` follows the existing `updatedAt` rule.
- Backups: ZIP `backup.json` gains a `categories` array (additive, `version` stays 2; older v2 files without it still import). Merge and delete semantics copy tabs (by id, own `updatedAt`, hard delete). After merging, an item whose `category` points to a category that doesn't exist locally or in the file is stored uncategorised (no failure); this also covers older backups without a `categories` array (my call).

## 3. Android navigation bar

- Problem (owner's report): with 3-button navigation, the system bar under the installed app shows white icons on a light background in the light theme — practically invisible.
- Requirement: the bar must be readable in light and dark theme, installed and in the browser. The builder researches the current Chrome/WebAPK behaviour (manifest `theme_color` / `background_color`, `theme-color` meta, `color-scheme`) and picks the fix; if Android can't be given dark icons on a light bar, use a dark bar colour in light theme too (e.g. `theme_color` dark) — readability beats colour matching. If a fallback colour is needed, use the app's dark text colour `#2b2620` for the bar and keep the status bar/splash as close to the palette as Android allows (my call). Verified by the owner on the real phone.

## 4. iOS

- Installation instructions adapt to the device: iPhone/iPad → "Condividi → Aggiungi alla schermata Home"; Android → Chrome menu → "Installa app". Also on the desktop invite page (QR + both instructions).
- **Data-loss warning on iOS**: Safari deletes site data after ~7 days without visits unless the app is installed. Detection is best-effort (iPhone/iPod UA, or iPadOS reporting "Macintosh" with touch points > 1), non-standalone only; "dismissible per session" via sessionStorage (my call). No equivalent banner on Android (Chrome is far less aggressive and the app already requests persistent storage). When running in Safari (not standalone) on iOS, show a persistent, dismissible-per-session banner explaining this and how to install. In standalone mode, no banner.
- Check and fix on iOS Safari: photo picking (camera/gallery, HEIC → decode or a clear skip message), WebP encoding fallback (already JPEG), backup export (share sheet with the ZIP if supported, else download/"open in" — the user must end up with the file in Files or iCloud Drive; copy adapted), import from Files, safe areas (notch, home indicator), viewer gestures vs Safari's own gestures (edge swipe back, pinch), `apple-touch-icon`, status bar style, no zoom on input focus (font-size ≥ 16 px in inputs).
- Tested on a real iPhone before release.

## 5. Accessibility

- Everything operable by keyboard and screen reader (TalkBack, VoiceOver): tiles are buttons with `aria-pressed` and a label (description, place, category); dialogs move focus in and restore it on close, Escape closes; the viewer has accessible controls (close, next/previous, rotate, edit) without relying on gestures.
- Contrast: text and essential icons meet WCAG AA (4.5:1 for text, 3:1 for large text/UI parts). The accent-on-cream combination (≈3.2:1) must be adjusted where it carries small text (e.g. darker accent text or bolder/larger labels) — keep the look; builder's call on exact values within the palette's spirit.
- Respects system text size (rem-based type, layout survives 200% text), `prefers-reduced-motion`, touch targets ≥ 44×44 px, visible focus styles.

## 6. Languages

- Italian and English. Default: Italian if the browser/phone language starts with `it`, otherwise English. Menu → Lingua / Language: Auto / Italiano / English (stored like the theme).
- All UI strings, alerts, dialog texts, error messages, import/export summaries, desktop invite, about footer, `lang` attribute. Default category names follow the language (see §2); user content never translated.
- Tab names (including "Nido"/"Materna" created by a v1 import) are user content and never translated (my call).
- Manifest stays Italian name/short name ("Andata e Ritorno", "A/R" — same in both). README gets an English main text with a short Italian section (or vice versa — builder's call, both present).
- Implementation: a small in-house dictionary module (`t(key, params)` with plural support for the handful of counted strings), no i18n framework.

## 7. Hardening

- **Security headers** on ar.gioxx.org (static assets via Workers): Content-Security-Policy allowing only self (scripts, styles, fonts, images incl. `blob:` and `data:` as needed by photos/QR), `frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` limited to what the app uses (camera via file input needs none). Delivered with a `_headers` file (or equivalent supported by Workers static assets; the builder verifies on the deployed site). Target: as strict as the build allows without `'unsafe-inline'` for scripts — the inline pre-paint theme script gets a hash or moves to a file; inline styles may need `'unsafe-inline'` for `style-src` if refactoring them is disproportionate (my call).
- **Schema upgrades**: IndexedDB version 2 adds `categories`; upgrade code must preserve all existing data (test from a real v1-schema DB with photos). Wire `setVersionChangeHandler` so an old open tab reloads/asks to reload instead of failing writes.
- **Large backups**: streaming ZIP export/import (fflate streaming APIs, Blob parts) so peak memory doesn't double the photo size; keep integrity checks and the busy overlay.
- **Deferred minors from v2** to close now: `updateItem` field whitelist in db.js; consistent handling of unknown ids; reorder tabs in one transaction; viewer pan bounds after rotation of the device; stale viewer history entry after reload; duplicated strings (now moved to the dictionary); import serialised with store mutations (`runExclusive`); tab order collisions after importing from another device; dead code (`markChanged`, duplicate `esc`).

## Constraints

- Local-first, no server-side data, same hosting (Cloudflare Workers static assets, `worker/wrangler.app.toml`).
- Plain JS + Vite as today; no UI framework, no i18n framework.
- Visual style "Y" unchanged (tokens in `app/src/styles.css`), except contrast fixes required by §5.
- All existing tests stay green; data paths (schema upgrade, rotation, categories in backups) get tests.
- Release only after: browser pass (controller), owner check on Android (navigation bar, rotation, categories) and on iPhone (§4).

## Decided with the owner

Rotation with a single clockwise button, saved only on confirmation; categories: one per item, defaults added only on request + fully editable list, global across tabs, tag filter with OR and one-tap clear, defaults include "Accessori", no "cambio completo"; iOS tested on a real iPhone; Italian + English with automatic choice and manual switch; the accessibility/hardening scope above as listed.

## Left to the builder

Exact UI placement and styling of the tag row and category management (menu entry "Gestisci categorie" next to "Gestisci schede" is the expected default), the Android bar fix, CSP details, dictionary structure, streaming ZIP internals, how filters reset (default: clear on tab switch), contrast values, test approach for iOS-specific behaviour.
